# Plan 162 — Transport-Independent Streaming Response Bodies

## Status

**READY FOR IMPLEMENTATION.**

Prerequisite: Plan 161 present. This plan is foundational for downstream application servers and must land before Python service streaming or FastCGI response adaptation.

## Goal

Extend the canonical response model so a Rust `Service` can return an incrementally produced body with bounded memory and transport backpressure without exposing Hyper types or surrendering runtime ownership of HTTP framing.

The resulting response API must support:

- static/file responses unchanged;
- buffered application responses;
- known-length streaming application responses;
- unknown-length streaming application responses framed correctly by the HTTP/1 runtime;
- cancellation and mid-stream failure without response-smuggling or connection reuse ambiguity.

## Current gap

`ResponseBody` currently supports `Empty`, `Bytes`, `File`, and `EmptyWithLength`. Canonical normalization therefore assumes a representation length is known before transport. Request bodies already have a transport-independent streaming abstraction; responses do not.

Do not solve this by exposing `hyper::Body`, `Frame`, or `Incoming` through `eggserve-core::primitives`.

## Target public model

Exact names may differ, but the stable shape should be equivalent to:

```text
ResponseBody
  Empty
  Bytes
  File
  Stream(ResponseStream)
  EmptyWithLength

ResponseStream
  one-shot byte stream
  optional known_length
  bounded chunk contract
  transport-neutral error type
```

`ResponseStream` should implement or wrap a standard Rust async stream interface if doing so does not expose Hyper or force unnecessary dependencies into callers. It must yield bytes/chunks and a small EggServe-owned error type.

## Ownership and framing rules

The runtime remains the only authority for `Content-Length`, `Transfer-Encoding`, and connection reuse.

### Known-length stream

- normalize metadata using the declared representation length;
- send `Content-Length` generated by EggServe;
- count emitted bytes;
- fewer or more bytes than declared is a stream/protocol failure;
- if failure occurs after response commitment, close the connection and emit structured diagnostics; do not attempt a second HTTP error response.

### Unknown-length stream

- do not synthesize `Content-Length`;
- let the HTTP/1 transport select correct chunked framing;
- service-provided `Transfer-Encoding` remains forbidden/stripped as runtime-owned;
- a successfully completed unknown-length stream may leave the connection reusable if Hyper/runtime framing completed cleanly.

### Empty and file bodies

Preserve existing semantics and optimized file capability handling. Do not route files through the general application stream unless measured evidence later justifies unification.

## HEAD and body-forbidden statuses

Canonical behavior is mandatory:

- `HEAD` never polls or consumes the response stream;
- if a HEAD response stream declares a known representation length, preserve that equivalent-GET length in metadata;
- if the equivalent body length is unknown, do not invent a `Content-Length`;
- 1xx, 204, 205, and 304 must not poll/send application body bytes;
- retain current special 304 metadata validation where standards permit it;
- dropping a suppressed stream must release all producer resources promptly.

Tests must prove that a stream with side effects is not polled for HEAD/body-forbidden responses.

## Backpressure and bounded memory

The transport must poll producers according to downstream write capacity. Do not insert an unbounded channel between application and socket.

If a channel is required for cross-language or cross-thread adaptation later, that channel belongs in the adapter and must be bounded. The canonical Rust stream itself should be pull/backpressure driven.

Define and validate:

- maximum individual application chunk size if a limit is needed;
- behavior for empty chunks;
- whether very large chunks are split by the runtime rather than rejected;
- cancellation/drop behavior when the client disconnects;
- producer wakeups and no busy loops.

Avoid copying chunks solely to satisfy the canonical abstraction. Prefer `bytes::Bytes` if it remains suitable for the stable public contract.

## Error and commitment model

Introduce an explicit concept in implementation/tests even if it is not public API:

1. **before response commitment** — a stream setup failure can still become a canonical 500/other allowed service error;
2. **after response commitment** — a producer failure terminates the response/connection and is observable internally only.

Never serialize producer error messages, panic payloads, filesystem paths, Python exceptions, or debug details to the client.

Panics while polling a Rust stream must be contained at a safe task boundary. If converting every stream panic into a response is impossible after commitment, close deterministically and log a sanitized event.

## Timeout integration

Plan 164 will add production response-write/no-progress controls. This plan must leave the body representation compatible with them.

For this phase:

- stream execution remains bounded by the applicable connection/shutdown lifetime;
- cancellation must stop producer polling promptly;
- shutdown must not wait forever on an application stream;
- do not misuse `handler_timeout` as a total lifetime for a long-lived streaming response unless current semantics explicitly require it; document any temporary limitation for Plan 164.

## Canonical normalization changes

Refactor `normalize_response()` / `normalize_metadata()` so body length is represented as `Known(u64)` vs `Unknown` rather than assuming every body has a `u64` length.

Required invariants:

- hop-by-hop/framing headers still removed centrally;
- known buffered/file bodies retain exact current Content-Length semantics;
- unknown body length never becomes `Content-Length: 0` accidentally;
- `EmptyWithLength` remains valid for adapter HEAD semantics if still needed;
- all response producers converge on one normalization policy before transport conversion.

## Public construction ergonomics

Provide a small constructor/builder path, for example:

```text
ResponseStream::new(stream)
ResponseStream::with_known_length(stream, len)
ResponseBody::Stream(...)
```

Do not require callers to understand chunked transfer coding.

Document a minimal example of a Rust service generating chunks. The example is illustrative, not a framework/router.

## Observability

Add bounded counters/events for at least:

- streaming responses started/completed;
- known-length mismatch;
- stream producer failure;
- stream producer panic if separately detectable;
- stream cancelled/client disconnected.

Do not log body contents.

## Tests

Add unit/integration/wire tests for:

- known-length stream success;
- unknown-length stream success and valid HTTP/1 framing;
- empty stream;
- multiple small chunks;
- large chunk;
- HEAD known length and unknown length without polling;
- 204/205/304 suppression without polling;
- service attempts to set `Content-Length`/`Transfer-Encoding`;
- exact known-length underrun and overrun;
- error before first data where recoverable;
- error after data/commit closes connection;
- client disconnect while producer pending;
- shutdown while producer pending;
- slow-reader backpressure with bounded memory;
- keep-alive request following a successful unknown-length response;
- unchanged file/range/static behavior;
- API snapshots/doc tests.

Include property tests for byte-count accounting if practical.

## Non-goals

Do not add in this plan:

- trailers;
- WebSockets/upgrades;
- SSE-specific APIs;
- compression;
- HTTP/2/3;
- Python iterator/async-generator response bodies;
- sendfile/io_uring changes;
- application routing or middleware.

Those consumers should use the generic stream primitive later.

## Acceptance criteria

- [ ] A Rust `Service` can return known- and unknown-length streaming bodies without importing Hyper.
- [ ] Unknown-length responses are framed by the runtime, not by the service.
- [ ] Known-length mismatch cannot yield a reusable ambiguous HTTP/1 connection.
- [ ] HEAD/body-forbidden paths do not poll application streams.
- [ ] Client backpressure bounds producer progress/memory.
- [ ] Cancellation/shutdown release stream resources.
- [ ] Existing static/file/range conformance remains unchanged.
- [ ] Stable API docs and the EggServe development skill describe the new response-body invariant.

## Handoff

Plan 163 may consume this body type over arbitrary transports. Plan 166 maps Python low-level producers onto this contract. Plan 167 uses it for gateway output. Plan 168 establishes performance and fault evidence.
