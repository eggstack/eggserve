# Plan 289 — Direct H1 service-response metadata ownership

Status: **IMPLEMENTED; qualification continues under Plan 290**.

Program:
`plans/288-291-direct-h1-boundary-ownership-followup-program.md`.

Planning baseline:
`2d4bae12f8cb87c01a8496d765d18b1380871e72`.

## Goal

Allow a direct-H1 embedder to explicitly own service-provided `Date` and
`Server` response metadata on a per-response basis while preserving
EggServe's framing authority, denylist behavior, runtime-generated error
privacy, and hardened defaults.

This is an embedding ownership seam, not a relaxation of response validation.

## Current behavior

At the planning baseline:

- Hyper automatic Date insertion is disabled;
- `ResponsePolicy` is runtime-global;
- `InFlightGuard::finish` runs `finalize_runtime_response` for every H1
  response;
- finalization always removes service `Server` and `Date`;
- `server_identification` is then inserted if configured;
- `DatePolicy` is then applied as the sole Date authority;
- `Last-Modified > Date` is dropped;
- runtime-generated errors and ordinary service responses take the same final
  metadata path;
- `RuntimeRejectionPresenter` intentionally cannot set `Date` or `Server`.

That is the right default for a standalone origin. It is too rigid for a
direct embedder that already owns per-response site/tenant metadata.

## Design constraint — do not mutate ResponsePolicy shape

Do not add fields to public `ResponsePolicy` or change the type of
`server_identification`. Both create avoidable source churn for exhaustive
struct literals.

Prefer a new additive ownership type attached only to the private-field
`H1ConnectionPolicy`.

Suggested public type:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub struct ResponseMetadataOwnership {
    pub date: PolicyOwner,
    pub server: PolicyOwner,
}
```

Default is all EggServe-owned.

Suggested additive policy API:

```rust
impl H1ConnectionPolicy {
    pub fn with_response_metadata_ownership(
        self,
        ownership: ResponseMetadataOwnership,
    ) -> Self;
}
```

Re-export the new type from `eggserve-server`.

Do not add a CLI/Python setting in this plan.

## Track A — explicit response provenance

The finalizer must distinguish:

- **service response** — returned successfully by `Service::call` /
  `call_with_tunnel`;
- **runtime response** — parser/validation/body/admission/service-error/panic/
  timeout/runtime-presentation fallback generated by EggServe.

Introduce a private explicit provenance marker rather than inferring from
status codes or headers.

Acceptable internal shapes include:

```rust
enum ResponseProvenance {
    Service,
    Runtime,
}
```

threaded through `finish_response` / `InFlightGuard::finish`, or an
equivalent private response envelope.

Do not use thread-local/task-local/global side channels.

## Track B — Date ownership semantics

### EggServe-owned Date

No behavior change:

- remove service Date;
- insert Date from `DatePolicy` when configured;
- preserve current default system-clock behavior;
- preserve current suppression/custom-provider behavior.

### External service Date

For a **service response only**:

- do not synthesize or overwrite Date;
- preserve intentional absence;
- preserve one valid service Date value exactly;
- validate the value as an HTTP-date before commit;
- multiple Date fields are invalid for this ownership mode and must fail
  safely before wire commit;
- an invalid/multiple service Date must become a generic runtime 500 using
  EggServe-owned runtime error metadata, not leak the invalid value;
- when a valid Date exists, retain the existing
  `Last-Modified <= Date` invariant;
- when Date is intentionally absent, use the same Last-Modified semantics as
  current Date suppression.

External Date ownership explicitly transfers RFC 9110 origin responsibility to
the embedding application. Documentation must say that an origin with a clock
is responsible for generating Date on the response classes required by RFC
9110.

Do not enforce "freshness" beyond syntactic/date parsing; an embedder may have
a legitimate custom clock or controlled jitter.

## Track C — Server ownership semantics

### EggServe-owned Server

No behavior change:

- remove service Server;
- suppress by default;
- insert the configured fixed `server_identification` when present.

### External service Server

For a **service response only**:

- preserve service-provided Server values;
- preserve intentional absence;
- do not insert runtime `server_identification`;
- retain canonical header-value validation, so CR/LF or invalid field values
  remain impossible;
- do not expose transport/runtime versions automatically.

The existing explicit stripped-header denylist still has higher precedence:
if an operator has chosen to strip `server`, external ownership must not
re-add it.

Do not introduce wildcard or project-specific header exceptions.

## Track D — runtime errors remain runtime-owned

Even when service Date/Server ownership is External:

- parser/target/header/body rejections;
- admission failures;
- handler timeout;
- service panic/error converted to runtime error;
- invalid external Date fallback;
- rejection presenter fallback

must continue through the current runtime `ResponsePolicy`.

That preserves deterministic error privacy and prevents a failed service
response from smuggling metadata through a runtime-generated 500.

`RuntimeRejectionPresenter` continues filtering Date/Server; do not widen its
authority in this plan.

## Track E — canonical/framing order

Preserve this order:

1. canonical response normalization/framing;
2. denylist;
3. Date/Server ownership decision;
4. Last-Modified vs effective Date check;
5. H1 lifecycle headers such as `Connection: close`;
6. body tracking/write progress.

External metadata ownership must never transfer:

- Content-Length;
- Transfer-Encoding;
- Connection;
- Keep-Alive;
- Upgrade;
- Trailer;
- Content-Range;
- other canonical framing/hop-by-hop authority.

## Track F — tunnel/upgrade responses

A successfully accepted service tunnel/upgrade handshake is service-origin
metadata for this purpose.

Prove:

- 101/CONNECT-style handshake framing stays EggServe-owned;
- external service Server can survive if deliberately supplied;
- Date may be absent on 1xx without runtime reinsertion under external
  ownership;
- forbidden handshake/framing headers remain runtime-controlled;
- ordinary declined tunnel paths follow normal service/runtime provenance.

Do not change tunnel capability ownership or transport behavior.

## Track G — tests

Add direct H1 tests proving two or more requests on the same runtime can carry
different service metadata:

1. service response A -> one valid Date + Server `alpha`;
2. service response B -> different valid Date + Server `beta`;
3. service response C -> Date absent + Server absent;
4. all three are preserved only under External ownership;
5. the default policy still overwrites/suppresses them exactly as before.

Also cover:

- invalid service Date -> generic 500, invalid value absent from wire;
- duplicate service Date -> generic 500;
- external Date + future Last-Modified -> Last-Modified removed;
- external Server + explicit server denylist -> Server removed;
- runtime 431/413/500 still uses runtime Date/Server policy;
- custom `RuntimeRejectionPresenter` still cannot set Date/Server;
- HEAD;
- 204/304;
- tunnel/101;
- streaming response;
- duplicate unrelated application headers unaffected.

## Track H — H2/H3 and high-level Server isolation

This plan is a direct-H1 embedding seam.

- ordinary `RuntimeConfig::h1_connection_policy()` remains EggServe-owned;
- high-level `eggserve-server::Server` therefore keeps current behavior;
- compatibility H2/H3 response policy remains unchanged;
- `finalize_canonical_response` used by H3 is not broadened by this plan;
- no support-tier change.

A future protocol-neutral ownership feature may generalize this after separate
evidence; do not broaden this implementation to solve hypothetical H2/H3
consumers.

## Documentation

Update direct-H1 embedding docs to distinguish:

- framing ownership;
- runtime-error metadata ownership;
- service-response metadata ownership.

Document the security tradeoff explicitly: External Date/Server ownership is
for embedding applications that already have a response-metadata policy. It is
not the hardened standalone default.

## Acceptance criteria

- [ ] a public additive Date/Server ownership type exists.
- [ ] default projected H1 policy remains fully EggServe-owned.
- [ ] service and runtime response provenance are explicit internally.
- [ ] external service Date preserves valid per-response values/absence.
- [ ] invalid or duplicate service Date fails before wire commit.
- [ ] external service Server preserves per-response values/absence.
- [ ] denylist still wins.
- [ ] runtime-generated errors remain EggServe metadata-owned.
- [ ] framing/hop-by-hop authority is unchanged.
- [ ] Last-Modified invariant is preserved.
- [ ] high-level Server/H2/H3 defaults are unchanged.
- [ ] focused tests and normal CI pass.

## Non-goals

- No per-request global/task-local mutation.
- No generic arbitrary-header ownership framework.
- No H2/H3 ownership expansion.
- No change to runtime rejection status/lifecycle semantics.
- No project-specific tenant/site abstraction.
