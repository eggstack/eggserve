# Plan 266 — Native ARM64, Windows ARM64, ARMv7, and real-SBC wheel qualification

## Purpose

Raise the evidence quality behind EggServe's ARM/SBC and Windows ARM64 wheel
claims. Cross-compilation is sufficient to create an artifact; it is not by
itself sufficient to prove that users on Raspberry Pi, Le Potato, ARM64 Linux,
or Windows ARM64 can install and run it.

Depends on Plans 263–265.

Planning baseline:

```text
09ada539 docs: simplify readme around python/rust quick starts
```

## Principles

- Prefer native execution when a standard hosted runner exists.
- Keep QEMU for ARMv7 where hosted native ARM32 is unavailable.
- Add a repeatable real-device qualification command/path, but do not make
  volunteer/self-hosted hardware a mandatory security boundary for every PR.
- Qualification must install the built/published wheel; a successful
  `cargo check --target` is not wheel evidence.
- Record userspace architecture and libc. Board marketing names are not wheel
  tags.

## Track A — Native Linux AArch64 qualification

Use the current standard GitHub ARM64 Ubuntu runner for an installed-wheel
qualification lane where available.

Two acceptable build patterns:

1. build the AArch64 wheel natively on the ARM64 runner; or
2. retain the maturin cross build for deterministic packaging, then download
   that exact artifact and execute it on the native ARM64 runner.

Prefer option 2 initially if it minimizes release-pipeline churn while still
providing native execution evidence. A later simplification may move the build
itself native after comparing wheel tags/composition.

Native smoke:

- binary-only wheel install;
- `import eggserve, eggserve._native`;
- CLI and `python -m eggserve` help;
- real loopback static-file request through `scripts/release_smoke.py`;
- representative filesystem confinement smoke;
- report `uname -a`, `platform.machine()`, Python version, and libc.

This lane is the representative evidence for 64-bit Raspberry Pi and Le
Potato-class Linux userspaces. Do not claim board-specific kernel/device
support beyond the userspace/architecture evidence.

## Track B — Native Windows ARM64 qualification

Move Windows ARM64 from cross-build-only confidence to native installed-wheel
qualification using the current hosted Windows ARM64 runner when available.

Requirements:

- install the exact `win_arm64` wheel generated by the release matrix;
- import native extension;
- run CLI/module smoke;
- run `scripts/release_smoke.py`;
- run the relevant non-destructive Windows filesystem qualification subset;
- record OS build, architecture, filesystem type, Python version, and wheel
  filename.

Reconcile `docs/toolchain-support.md`: it must not simultaneously call
Windows ARM64 Tier 1 and state that native ARM64 execution is still a
prerequisite for Tier 1.

The existing Windows trusted/local-content security qualification remains
unchanged unless the executed filesystem tests provide evidence for a
separate security-tier change; this plan does not authorize one.

## Track C — ARMv7 QEMU qualification

Keep QEMU ARMv7 as a required release gate for both:

- manylinux/glibc ARMv7;
- musllinux ARMv7 from Plan 265.

The test must execute the wheel under an ARMv7 userspace matching the wheel
family. Do not use an AArch64 container with compatibility mode as the only
proof.

Run the same compact release smoke used by other target lanes and verify that
pip selects the expected platform wheel without a build fallback.

## Track D — Real SBC qualification harness

Add a portable manual script, for example
`scripts/qualify-python-wheel-target.sh`, that can be run on:

- Raspberry Pi OS / Debian / Ubuntu ARM64;
- Armbian/Debian on Le Potato or similar AArch64 boards;
- Raspberry Pi OS ARMv7;
- Alpine ARM64/ARMv7 where available.

Inputs should support either:

- a local wheel path from a downloaded release artifact; or
- package/version/index for post-publication qualification.

The script records:

- package version and wheel filename;
- Python version;
- `platform.machine()`;
- OS release;
- libc family/version where discoverable;
- import result;
- CLI/module result;
- real loopback server smoke result.

It must not require root.

Do not commit hardware-specific hostnames, credentials, tokens, or runner
labels. If maintainers later register self-hosted runners, that is operational
configuration, not part of the portable product contract.

## Track E — CPython endpoint coverage on representative architectures

Plan 264 proves all minors on Linux x86_64. This plan adds architecture-aware
endpoint checks:

- minimum CPython 3.11 on at least Linux AArch64;
- CPython 3.15 on at least Linux AArch64;
- current available supported CPython on ARMv7;
- current available supported CPython on Windows ARM64.

Do not require every Python minor on every architecture; `abi3` is already
proven exhaustively on the representative host, while these lanes prove
platform execution.

## Track F — Post-publication matrix

Expand post-publication smoke so it covers at least:

- Linux x86_64 glibc;
- Linux AArch64 glibc;
- Linux ARMv7 glibc;
- Linux x86_64 musl;
- Linux AArch64 musl;
- Linux ARMv7 musl;
- macOS arm64;
- Windows x86_64;
- Windows ARM64.

If a hosted runner cannot execute one target, retain the pre-publication
QEMU/native proof and document the post-publication limitation rather than
pretending it was tested.

All install steps use binary-only resolution and capture the resolved wheel.

## Evidence and documentation

Add a compact release qualification record under `release/` when the plan is
executed, containing:

- source SHA;
- workflow run;
- built wheel list and SHA-256 manifest;
- native/QEMU runtime matrix;
- real-SBC evidence if executed;
- any blocked hardware/runtime lane;
- exact support claims retained after the evidence.

Update `docs/toolchain-support.md` and `docs/release-process.md` to
distinguish:

- build support;
- emulated runtime qualification;
- native hosted qualification;
- optional real-device qualification.

## Acceptance

- Linux AArch64 wheel executes on a native ARM64 hosted runner.
- Windows ARM64 wheel executes on a native ARM64 Windows hosted runner, if the
  current GitHub-hosted offering is available to this repository; otherwise
  the blocker is recorded and the support wording remains conservative.
- ARMv7 glibc and musl wheels execute under matching ARMv7 runtime environments.
- real-device qualification is reproducible with one rootless script.
- Raspberry Pi/Le Potato claims are stated in terms of supported ARM
  userspaces, not unverified board-specific hardware behavior.
- no API or protocol/security-tier change.
